### Звіт аудитора і виправлення

| № | Знахідка у v1 | Виправлення |
|---|---|---|
| 1 | `NicheViewSet` звертається до Django ORM напряму в обхід сервісу — порушення ізоляції домену | Контролери викликають лише Application Services; доступ до даних — через порти |
| 2 | `ScoringService` залежить від конкретних моделей Django ORM (Tight Coupling) | Введено `Ports` (Python Protocol) і Outbound-адаптери; ядро не імпортує ORM, Redis, Celery (DIP) |
| 3 | Відсутні автентифікація, rate limiting і перевірка прав | Додано JWTAuthentication, UserRateThrottle, RoleAndOwnershipPermission (Guard) |

| 5 | Відсутні логування, метрики, трасування | Додано ObservabilityMiddleware (OpenTelemetry, prometheus_client, JSON-логи) |

| 7 | Кеш рейтингу може повертати застарілі дані | Ключ кешу містить `scoring_run_id` |

## Сесія 4. ADR Reviewer

### Промпт

```text
Роль: Chief Technology Officer (CTO), Principal Enterprise Architect та суворий рецензент технічних
компромісів в ІТ-індустрії.
Моя специфікація вимог (SRS): [docs/srs.md]
Моя чернетка ADR за Нігардзом: [ADR-001: Celery + Redis проти Kafka і RabbitMQ]
Твоє завдання: 1) критика аргументації (метрики замість «популярний/зручний»); 2) об'єктивність
мінусів альтернатив; 3) чесність негативних наслідків (CI/CD, FinOps, Vendor Lock-in).
```

### Звіт рецензента і рішення

| № | Пункт перевірки | Результат |
|---|---|---|
| 1 | Порівняння має спиратися на числа: обсяг ≤ 10⁵ документів/добу ≈ 1,2 задачі/с | Враховано в чернетці, підтверджено аудитом: потреба і запас пропускної здатності наведено в Alternatives і Decision |
| 2 | FinOps: споживання пам'яті Kafka і RabbitMQ на одному вузлі 8 GiB | Враховано в чернетці, підтверджено аудитом: рядок «Додаткова інфраструктура» з оцінками RAM |
| 3 | SPOF Redis і ризик втрати задач без AOF | Враховано в чернетці, підтверджено аудитом: два негативні наслідки з пом'якшенням (AOF, повторна постановка `PENDING` запусків) |
| 4 | Ліцензія Redis 8 (AGPLv3) — ризик Vendor Lock-in | Враховано в чернетці, підтверджено аудитом: наслідок із альтернативою Valkey (BSD 3-Clause) |
| 5 | Не описано вплив на CI/CD | Додано після аудиту: потреба сервісного контейнера Redis у GitHub Actions |
| 6 | Перевага Kafka — replay подій — потребує спростування | Враховано в чернетці, підтверджено аудитом: обґрунтовано, що джерелом істини є PostgreSQL, replay не потрібен |
| 7 | Рекомендація: Redis Sentinel для усунення SPOF | Відхилено: потребує ≥ 3 вузлів Sentinel, що виходить за межі одновузлового розгортання; ризик прийнято і задокументовано |

Підсумок: після аудиту додано наслідок для CI/CD; розуміння вибору змінилося з «Celery достатньо» на кількісне обґрунтування з явно прийнятими
ризиками (SPOF Redis, at-least-once, ліцензія).
