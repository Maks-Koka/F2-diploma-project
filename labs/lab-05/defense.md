## Текст

**0:00–1:20. SRS.** Специфікацію побудовано за структурою ISO/IEC/IEEE 29148: межі системи, контекст із
зовнішніми інтерфейсами і лімітами джерел, класи користувачів, обмеження і припущення. Функціональні
вимоги мають ідентифікатори від SRS-FUN-01 до 25 і модальне дієслово «повинна». Початково їх було 16,
але аудит виявив складені вимоги: наприклад, перевірка ролі і перевірка належності об'єкта були в
одному пункті. Тепер роль перевіряє SRS-FUN-03 з кодом 403, а належність — SRS-NFR-SEC-03 з кодом 404,
щоб не розкривати існування чужих проєктів. Двадцять три нефункціональні вимоги мають індекси за
категоріями ISO 25010 і числа. Таблиця верифікації для кожної вимоги називає метод і інструмент:
pytest, Postman, k6, SonarQube, Trivy, Prometheus, OWASP ZAP. Глосарій містить сім термінів.

**1:20–2:40. C4 Level 1–2.** На контекстній діаграмі два актори і чотири зовнішні API; кожна стрілка
підписана протоколом, наприклад «REST/JSON, HTTPS, GET, Bearer token» для GitHub. Діаграма контейнерів
подана у двох представленнях, бо чотирнадцять контейнерів на одній схемі давали накладання підписів.
Прикладний контур: Nginx як API Gateway, Next.js, Core API на Django, окремі Ingestion і Analytics Worker,
Scheduler, Redis, PostgreSQL primary і replica. Другий контур — OpenTelemetry Collector, Prometheus,
Jaeger, Grafana і WAL-архів. Під діаграмами таблиці з протоколами і посиланнями на конкретні вимоги SRS.

**2:40–3:50. C4 Level 3.** Для декомпозиції обрано Core API як точку входу всіх сценаріїв і контур
безпеки. Запит проходить ObservabilityMiddleware, JWTAuthentication, UserRateThrottle і Guard ролі та
належності. Контролери не містять бізнес-логіки і не звертаються до ORM: вони викликають прикладні
сервіси, а ті працюють через порти — інтерфейси репозиторіїв, кешу, черги і аудиту. Адаптери
реалізують порти, тобто залежності спрямовані до ядра. DTO відхиляють невідомі поля, глобальний
обробник повертає єдину схему помилки з trace_id. Задача оцінювання публікується лише після фіксації
транзакції.

**3:50–4:40. ADR-001.** Рішення стосується механізму асинхронної обробки. Розглянуто Celery з Redis,
Kafka і Celery з RabbitMQ. Обсяг до ста тисяч документів на добу — це близько 1,2 задачі за секунду,
тому розподілений журнал Kafka надлишковий і потребує щонайменше гігабайта пам'яті на брокер. Обрано
Celery з Redis, бо Redis уже потрібен для кешу. Негативні наслідки названо прямо: Redis стає
одиничною точкою відмови, доставка at-least-once вимагає ідемпотентних задач, ліцензія Redis 8 —
AGPLv3, а CI потребує сервісного контейнера Redis.

**4:40–5:00. Git.** PR із гілки `feature/chapter2-architecture`, коміти за Conventional Commits, README
містить навігацію на SRS і ADR.

## Можливі питання викладача

| № | Питання | Коротка відповідь |
|---|---|---|
| 1 | Чим контейнер відрізняється від компонента? | Контейнер — окремо розгортуваний процес (Docker-контейнер), компонент — модуль коду всередині контейнера |
| 2 | Чому Core API, а не Analytics Worker, для C4 L3? | Core API містить усі шари захисту і узгодження з конвеєром; алгоритми воркера деталізовано в ЛР№6 |
| 3 | Як реалізовано Dependency Inversion? | Ядро залежить від портів (Python Protocol), адаптери ORM, Redis, Celery реалізують порти |
| 4 | Чому невласник отримує 404, а не 403? | 403 підтверджує існування ресурсу; 404 унеможливлює перебір ідентифікаторів (захист від IDOR/BOLA) |
| 5 | Як верифікується SRS-NFR-PERF-01? | k6, сценарій constant-arrival-rate 200 RPS, 10 хв, пороги p(95) < 200 мс і http_req_failed < 0,5 % |
| 6 | Чому не Kafka? | Потреба ≈ 1,2 задачі/с; Kafka додає брокер і контролер, не дає переваги без потреби в replay подій |
| 7 | Яка головна вада обраного рішення? | Redis — SPOF для черги, кешу і лімітів; пом'якшення: AOF, health check, повторна постановка PENDING-запусків |
| 8 | Чому модульний моноліт? | Один розробник, спільна транзакційна БД, обсяг до 10⁵ документів/добу; межі модулів дозволяють виділення сервісів пізніше |
| 9 | Як працює трасування вимог? | У таблицях під діаграмами відносні посилання `srs.md#srs-fun-NN` і на ADR; матриця трасування в SRS |
