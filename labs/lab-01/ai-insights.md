## 1. Початковий текст (вхідні дані студента)

> Тема (робоча назва UA): «Інтелектуальна платформа виявлення та оцінювання ринкових можливостей».
> Суть: система знаходить незадоволений попит. Збирає дані з відкритих безкоштовних джерел, виявляє
> повторювані скарги та проблеми, групує потреби за темами, порівнює конкурентів, ранжує ніші за
> ПРОЗОРИМИ критеріями. Кожна рекомендація містить оцінку, джерела даних, аргументи «за», ризики, рівень
> невизначеності та пояснення, чому саме такий рейтинг. Це НЕ «AI-звіт»: ранжування має бути
> відтворюваним і пояснюваним.
> Обмеження: жодних платних сервісів і платних API.
> Стек: Frontend — Next.js + TypeScript + Tailwind CSS. Backend — Django (Python) + Django REST
> Framework. БД — PostgreSQL (за потреби pgvector). Фонові задачі — Celery + Redis. Дані та ML — pandas,
> scikit-learn. Тести — pytest. Контроль версій — Git + GitHub. Контейнеризація — Docker / Docker Compose.

## 3. Аналітичні рекомендації ШІ

### 3.1. Відповідність рівню F2

- Вихідний опис відповідає Напряму 2 (AI & Data Engineering) і частково Напряму 4 (Quality Engineering).
  Ризик зведення до CRUD відсутній: система містить конвеєр обробки даних і обчислювальне ядро.
- Прогалини: не визначено архітектурний тип, відсутні механізми відмовостійкості збору даних, не описано
  безпеку, спостережуваність і контроль якості; «прозорість» не формалізовано як вимірювану властивість.

### 3.2. Запропоновані ускладнення та рішення щодо них

| № | Рекомендація ШІ | Рішення | Обґрунтування |
|---|---|---|---|
| 1 | Виділити асинхронний конвеєр (брокер повідомлень, окремі обробники) | Прийнято: Celery + Redis, окремі Ingestion і Analytics Worker | Відповідає стеку; ізолює тривалі операції від HTTP-запитів |
| 2 | Замінити брокер на Apache Kafka | Відхилено | Обсяг подій (≤ 10⁵ документів/добу) не потребує розподіленого журналу; Kafka збільшує інфраструктурні витрати |
| 3 | Ідемпотентність задач збору, ключ ідемпотентності | Прийнято (CF-01) | Повторний запуск не повинен дублювати документи |
| 4 | Retry з експоненційним backoff, Circuit Breaker на джерело | Прийнято | Ізоляція збоїв зовнішніх API |
| 5 | API Gateway / reverse proxy, rate limiting, CORS | Прийнято: Nginx + ліміти в Django | Єдина точка входу, TLS-термінація |
| 6 | Автентифікація OAuth2/OIDC з JWT, RBAC | Прийнято: OAuth 2.0-сумісна видача JWT (RS256), ролі ANALYST/ADMIN | Захист від BOLA/IDOR, розмежування прав |
| 7 | Реплікація БД і резервне копіювання | Прийнято: streaming replica + WAL-архівування | Вимоги до RPO/RTO |
| 8 | Observability: OpenTelemetry, Prometheus, Grafana | Прийнято | Вимірювання p95 Latency і стану черг |
| 9 | CI/CD з SonarQube, Trivy, k6 | Прийнято (GitHub Actions) | Автоматизований контроль технічного боргу та вразливостей |
| 10 | Патерн Saga для узгодження стану | Відхилено | Система не має розподілених транзакцій між сервісами; узгодженість забезпечують транзакції PostgreSQL |
| 11 | Формалізувати «прозорість»: версіонована модель оцінювання, довірчий інтервал, перелік доказів | Прийнято (CF-06, CF-07) | Перетворює якісну вимогу на перевірну |
