## Сесія 1. Краш-тест обґрунтування архітектури (2.1)

Промпт: «Chief Enterprise Architect, CTO та цинічний Technical Lead… 1) архітектурні протиріччя і
"вода"; 2) атака на патерни коду; 3) Requirements Gaps & Edge Cases (Eventual Consistency, SPOF,
каскадні збої, FinOps)». Вхід: стек, коди C4 Container/Component, текст 2.1.

| № | Зауваження техліда | Відповідь у фінальному тексті |
|---|---|---|
| 1 | Твердження «моноліт простіший» без чисел | Аргумент через обсяг ≈ 1,2 задачі/с і відсутність розподілених транзакцій |
| 2 | Протиріччя: на C4 L2 Web App передає Bearer JWT, а в AppSec токени зберігаються в cookie | Уточнено: браузер передає cookie `HttpOnly` до SSR-сервера Next.js, який формує заголовок Bearer для Core API |
| 3 | CQRS заявлено в стеку, але на схемах немає окремих моделей читання | Повний CQRS відхилено як надлишковий; описано спрощену форму (репліка + кеш) |
| 4 | Не показано, що відбувається без Circuit Breaker | Кількісний сценарій: до 15 хв блокування обробника на запуск |
| 5 | Не описано вікно eventual consistency між збором і рейтингом | Ланцюжок `collect → detect_and_cluster → score`, ізоляція за `scoring_run_id`, читання власного запису з primary |
| 6 | SPOF замовчено | Перелік SPOF (Redis, primary, вузол) з пом'якшенням і прийнятим ризиком |
| 7 | Немає FinOps | Бюджет пам'яті ≈ 6,5 GiB на вузлі 8 GiB; економія від відмови від Kafka і Keycloak |

## Сесія 3. Краш-тест топології API і потоків даних (2.5)

Промпт: «Principal Integration Architect, Network Security Engineer… 1) розбіжності таблиці і
`openapi.yaml`; 2) дірки безпеки (query-параметри з токенами, захист мутуючих маршрутів);
3) Max Body Size, пагінація, CORS, Rate Limiting».

| № | Знахідка | Виправлення |
|---|---|---|
| 1 | Звірка таблиці з контрактом | 17 рядків = 17 операцій `openapi.yaml`, методи і шляхи збігаються (`x-route-id`) |
| 2 | Пояснення ніші допускало IDOR через підміну `nicheId` | Додано перевірку `niches.project_id = projectId` (Data Flow 3, UC-05 крок 2) |
| 3 | Не зазначено, що токени не передаються в query | Окреме правило: лише тіло або `Authorization`; маскування в журналах Nginx |
| 4 | Ліміт тіла і CORS не прив'язані до компонента | `client_max_body_size 1m` (413) і CORS у Nginx (Data Flow 1, крок 2) |
| 5 | Пагінація без верхньої межі | `page_size` 1–100, `page` ≤ 10 000; > 100 — 400 |

## Сесія 4. AppSec краш-тест серверного ядра (2.3.1, 2.4)

Промпт: «Principal Application Security Engineer, DevSecOps Architect, білий хакер… 1) Security
theater; 2) OWASP Top 10: SQLi, Mass Assignment, BOLA/IDOR; 3) Brute-Force, JWT на клієнті, Audit
Logging, секрети, сканування залежностей».

| № | Знахідка | Виправлення |
|---|---|---|
| 1 | «Паролі захищені» без параметрів | Argon2id 64 MiB / 3 / 4; refresh-токени лише як SHA-256 |
| 2 | Не описано реакцію на крадіжку refresh-токена | Повторне використання відкликаного токена відкликає весь ланцюжок |
| 3 | Brute-force лише rate limiting на IP | Додано блокування облікового запису на 15 хв після 10 невдалих входів |
| 4 | SSRF через URL конкурента | Сервер не завантажує `website_url`; адреси джерел фіксовані |
| 5 | Журнал аудиту можна змінити | Append-only, заборона UPDATE/DELETE правами ролі БД |
| 6 | Ротація ключа підпису JWT не описана | Ротація кожні 90 діб з `kid` у JWKS |
