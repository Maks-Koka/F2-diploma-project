## Context

Збір даних з чотирьох зовнішніх API і аналітична обробка (класифікація скарг, кластеризація,
bootstrap-оцінювання) тривають від десятків секунд до 10 хв на один проєкт. Виконання цих операцій у
межах HTTP-запиту несумісне з вимогою [SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03) (постановка в чергу
з p95 ≤ 150 мс) і з тайм-аутами reverse proxy (60 с). Тому потрібен механізм асинхронного виконання
задач з такими властивостями:

- доставка задачі принаймні один раз (at-least-once) і повторні спроби з експоненційним backoff, не
  більше 5 ([SRS-NFR-REL-03](../srs.md#srs-nfr-rel-03));
- окремі черги для збору (обмеженого I/O та лімітами джерел) і аналітики (обмеженої CPU) з незалежним
  горизонтальним масштабуванням ([SRS-NFR-SCAL-01](../srs.md#srs-nfr-scal-01));
- планування періодичних задач (повторний збір, очищення даних старших за 180 діб);
- інтеграція з Django ORM і транзакціями PostgreSQL.

Обмеження: розробник — одна особа; розгортання — Docker Compose на одному вузлі (4 vCPU, 8 GiB RAM);
очікуваний обсяг — до 10⁵ документів на добу; лише безкоштовні компоненти; стек зафіксовано
(Django, Celery, Redis, PostgreSQL). Redis уже потрібен системі як кеш і сховище лічильників rate
limiting.

## Alternatives

| Критерій | A1. Celery + Redis (брокер) | A2. Apache Kafka + окремі консюмери | A3. Celery + RabbitMQ |
|---|---|---|---|
| Модель доставки | Черга задач, at-least-once після `acks_late`; без довготривалого журналу | Розподілений журнал з партиціями, зберігання подій, повторне читання за offset | Черга AMQP 0-9-1 з підтвердженнями, at-least-once |
| Повтори і backoff | Вбудовані (`autoretry_for`, `retry_backoff`, `max_retries`) | Реалізуються вручну (retry-топіки, DLQ) | Вбудовані в Celery |
| Планування задач | Celery Beat | Відсутнє, потрібен окремий планувальник | Celery Beat |
| Додаткова інфраструктура | 0 нових контейнерів (Redis уже використовується) | Kafka-брокер + KRaft-контролер; ≥ 1 GiB RAM на брокер | 1 контейнер RabbitMQ (≈ 150–200 MiB RAM) |
| Пропускна здатність | Тисячі задач/с — з запасом відносно потреби (≤ 10⁵ документів/добу ≈ 1,2/с) | Сотні тисяч повідомлень/с — надлишкова для обсягу | Тисячі повідомлень/с |
| Інтеграція з Django | Нативна (`transaction.on_commit`, django-celery-beat) | Через бібліотеки клієнтів, без інтеграції з ORM | Нативна через Celery |
| Відтворення історії подій | Не підтримується | Підтримується (replay) | Не підтримується |

Альтернатива A4 (синхронна обробка в Gunicorn з потоками) відкинута без детального аналізу: вона
порушує [SRS-NFR-PERF-03](../srs.md#srs-nfr-perf-03) і блокує воркери HTTP на час збору.

## Decision

Обрано A1: Celery 5 з Redis 8 як брокером і бекендом результатів у межах модульного моноліту на
Django. Задачі розподілено між двома чергами: `ingestion` (Ingestion Worker, concurrency 8, I/O) і
`analytics` (Analytics Worker, concurrency = кількість vCPU, CPU). Для гарантії доставки
застосовуються `acks_late=True`, `task_reject_on_worker_lost=True`, `visibility_timeout` 3 600 с.
Задачі ідемпотентні: стан і курсор запуску зберігаються в PostgreSQL, повторне виконання продовжує
збір із курсора (алгоритм ALG-01). Задача публікується лише після фіксації транзакції
(`transaction.on_commit`), тому неіснуючий у БД запуск не потрапляє в чергу.

Обґрунтування: вимоги до повторів, черг і планування закриваються штатними механізмами Celery без
власного коду; інфраструктура не зростає, бо Redis уже присутній; пропускна здатність Redis-брокера
перевищує потребу більш ніж на три порядки. Можливість відтворення історії подій (перевага Kafka) не
потрібна: джерелом істини є PostgreSQL, а повторний розрахунок рейтингу виконується з таблиць, а не з
журналу подій.

## Consequences

Позитивні:

- Постановка задачі займає одну транзакцію PostgreSQL і одну операцію `LPUSH` у Redis, що забезпечує
  p95 ≤ 150 мс для `POST …/collection-runs`.
- Масштабування обробки — збільшення кількості контейнерів Analytics Worker (`docker compose up
  --scale analytics-worker=4`) без змін коду.
- Повтори, backoff і планування реалізуються конфігурацією Celery; кількість власного
  інфраструктурного коду мінімальна.
- Єдиний стек Python для API і обробників спрощує тестування pytest.

Негативні (компроміси і ризики):

- Redis стає точкою концентрації трьох функцій (брокер, кеш, лічильники лімітів). Відмова Redis
  зупиняє постановку задач і rate limiting одночасно — Single Point of Failure на одному вузлі.
  Пом'якшення: AOF-персистентність (`appendfsync everysec`), health check контейнера, окремі логічні
  бази db0–db2; Redis Sentinel або репліка не входять у межі роботи.
- Redis-брокер не гарантує збереження задач при аварійному завершенні без AOF; з `appendfsync
  everysec` можлива втрата задач за останню секунду. Пом'якшення: стан запусків у PostgreSQL і задача
  Celery Beat, що кожні 5 хв повторно ставить у чергу запуски в статусі `PENDING` старші за 10 хв.
- Модель at-least-once з `acks_late` допускає повторне виконання задачі; коректність залежить від
  ідемпотентності кожної задачі, що ускладнює код збору і тести (потрібні тести повторного виконання).
- Ускладнюється CI/CD: інтеграційні тести задач потребують сервісного контейнера Redis у GitHub
  Actions і режиму `task_always_eager` лише для модульних тестів, що збільшує тривалість конвеєра
  приблизно на час запуску контейнера Redis.
- Відсутній журнал подій: аналіз «що відбулося» спирається на журнал аудиту і трейси, а не на replay.
- Redis 8 розповсюджується під AGPLv3 (поряд із RSALv2/SSPLv1). Використання без модифікацій як
  внутрішнього сервісу не створює обов'язків щодо розкриття коду, але зміна вихідного коду Redis
  потребувала б юридичної оцінки; альтернативою з ліцензією BSD 3-Clause є Valkey з сумісним протоколом.
- Перехід на мікросервіси або потокову обробку в майбутньому потребуватиме заміни брокера; межі
  модулів (`ingestion`, `analytics`, `scoring`) і порт `TaskPublisherPort` локалізують цю зміну.
